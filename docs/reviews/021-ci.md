## VERSION survives the step boundary

Step 5 writes `VERSION=5d28f1fc` to `GITHUB_ENV`. Step 6, in a separate shell, sees it and
compose resolves the commit tag rather than `VERSION=dev` from `.env`:

```
VERSION seen by this step: 5d28f1fc
    image: distrolearn-api:5d28f1fc
    image: distrolearn-workers:5d28f1fc
```

The binary agrees:

```
api-1  | INFO api starting version=5d28f1fc
workers-1 | INFO workers starting version=5d28f1fc
```

The shell value beats `.env` because compose ranks the process environment above the file.
Had the export not gone through `GITHUB_ENV`, step 6 would have tagged `:dev` and run an image
step 5 never built, exactly as the comment at `compose.yml:62-66` says.

## Permissions and secrets

`permissions: contents: read` at the top level of both workflows, no job-level override
anywhere. No `secrets.` reference and no `${{ secrets }}` interpolation in either file. Every

## Trigger: every pull request, no path filter

The ticket asks this directly. Neither workflow has a path filter.

```yaml
# ci.yml
on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

# compose.yml
on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:
```

`pull_request:` with an empty value means every pull request, whatever it touches. There is no
`paths:`, no `paths-ignore:`, no `dtypes:` and no `tags:` anywhere in `.github/workflows/`. The
only filter is `push: branches: [main]`, which is the correct shape for a push trigger. So a
docs-only pull request runs both jobs, including the full compose build and the ADR 0006
variants. That is the plan's intent, since finding A is about a migration file and a migration
lives under `services/`, but it is worth knowing the cost before the repo grows.

## Finding 1: probe 2 in the plan cannot work as written

`docs/plans/021-ci-integration.md` lines 149-152. The plan says to add
`services/migrations/00002_probe.sql`, neuter step 5, and expect "the job goes green with
goose at version 1, reproducing finding A on the runner".

Measured, it goes to version 2. With step 5 neutered and the image absent from the daemon,
step 6 tries to pull the image first and then builds it:

```
Image distrolearn-api:5d28f1fc Pulling
pull access denied for distrolearn-api, repository does not exist or may require 'docker login'
...
#11 [api deps 4/4] COPY services/ ./
#12 [api build-api 1/1] RUN CGO_ENABLED=0 GOOS=linux go build ... ./api/cmd/api
```

The `COPY services/ ./` carries `00002_probe.sql` into the binary. Extracted `/service` from
the implicitly built image contains `00002_probe`. Bringing the stack up on that image:

```
max version_id: 2
api-1 | INFO goose: successfully migrated database to version: 2
```

Two separate problems.

The probe cannot reproduce finding A on a hosted runner, because finding A is about a stale
image already sitting on the daemon and a hosted runner starts empty every run. The plan says
so itself at lines 116-117, then asks probe 2 to do the thing those lines rule out. The build
step is still worth having, for the reason at lines 118-119, but it is not a staleness guard
in this environment.

The probe has no observation point. No step prints the goose version, and the only step that
would show it is `Dump compose state`, which runs `if: failure()`, while probe 2 expects a
green job. So even if the numbers came out as the plan predicts, the operator would have to
add a step the probe does not ask for.

PR #17, `docs(plan): correct probe 2 of plan 021`, rewrites the probe to introduce a compile
error and asserts the build step fails with compiler output naming the file and line. Its
rationale, that `up` builds whatever is missing on an empty daemon, matches this measurement.
The correction is already open and this finding agrees with it.

## Finding 2: the PR body records neither probe

The plan requires evidence at lines 147 and 152: "Paste the run URL into the PR body" for
probe 1, and "Both halves are in the PR body" for probe 2. The body has a SHA table and a
reviewer-action note, and nothing else. The runs exist and are readable, so this is a missing
record rather than a missing test, but a reviewer of the merged commit has no link to the red
run that proves the gate works.

## Finding 3: the SHA table covers two of four

ADR 0007 line 57 says each SHA is resolved when the pin is written and the resolution is
recorded in the pull request body. The body lists `actions/checkout` and `actions/setup-go`,
the two in the new file, and opens with "Both tags are lightweight". The other two pins live
in `ci.yml`, which this diff does not touch, so re-deriving them is arguably outside the
ticket. All four were resolved during this review and all four match, so nothing is wrong with
the pins. The table simply reads as a statement about the repository when it is a statement
about one file.
