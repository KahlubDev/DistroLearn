## The path filter question

Neither workflow has a path filter. `grep -rn paths .github/` returns nothing. Both `on:`
blocks are identical, `ci.yml` lines 3-7 and `compose.yml` lines 3-7:

```yaml
on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:
```

`pull_request` carries no `paths`, no `paths-ignore`, no `types`, and no `branches`. It
fires for every pull request, so a docs-only pull request queues both workflows. There is
no pending-forever failure mode from a path filter on this repository today. Adding a filter
later is what would create it.

`main` is not protected right now:

```
$ gh api repos/KahlubDev/DistroLearn/branches/main/protection
{"message":"Branch not protected", "status":"404"}
```

A ruleset named `main-protection` exists, id `24800236`, and its condition is
`"include": ["~DEFAULT_BRANCH"]`. The repository default branch is `docs/product-research`,
not `main`. Its `required_status_checks` rule carries an empty list. So there is no
protection rule on `main` to add a check to. Whoever turns this on has to create one, and
has to point it at `main` by name.

## Adding the check now would block every pull request

## Pull requests from forks

The trigger is `pull_request`, not `pull_request_target`, so a fork's pull request runs the
workflow from the merge ref with a read-only `GITHUB_TOKEN` and no repository secrets. The
repository is public with `allow_forking: true`.

The job reads no secret. It copies `.env.example` to `.env` and every credential is a
placeholder in that file. `grep -rn 'secrets\.' .github/` returns nothing, and both
workflows set `permissions: contents: read` at the top level with no `write` anywhere. A
fork cannot get anything from this job that it could not get from running the same commands
locally.

Two operational notes. First, on a public repository a workflow run from a first-time
contributor waits for maintainer approval before it starts, so the check stays pending
until someone clicks approve. That is a manual gate on external contributions, not a hang.
Second, `concurrency: group: compose-${{ github.ref }}` uses `refs/pull/N/merge`, so every
pull request gets its own group and repeated pushes queue rather than cancel. With a
20-minute timeout and a job that takes about 110 seconds end to end, a burst of pushes
drains without blocking a merge indefinitely.

## Verdict on making it required

Safe, in this order:

1. Merge PR #16.
2. Confirm a push to `main` reports `tenant isolation (compose)`.
3. Create a branch protection rule on `main` (there is none today) or correct the
   `~DEFAULT_BRANCH` condition on ruleset `24800236` so it names `main`.
4. Add `tenant isolation (compose)` as a required status check.

Turning the check on before step 1 blocks every pull request. Leaving the ruleset pointed at
`docs/product-research` means the check guards a branch nobody merges into.

## The pool mode assertion

`compose.yml` lines 80-93 reads `SHOW CONFIG` from the running pooler over the
`pgbouncer_admin` console, not from the ini file, and exits 1 unless the mode is
`transaction`.

Positive direction, three separate runner logs, including the probe 1 run above:
`pool_mode = transaction`.

Negative direction, run locally in the fresh clone. Set `pool_mode = session` in
`docker/pgbouncer/pgbouncer.ini.template`, bring the stack up healthy, then run the step's
shell verbatim. Local Compose was v5.5.1 rather than the runner's v2.38.2; what this checks
is PgBouncer's `SHOW CONFIG` output and the shell comparison, neither of which changes with
the Compose version.

```
$ docker compose up -d --wait --wait-timeout 300      # exit 0, all containers Healthy
pool_mode = session
::error::pool_mode is session, want transaction (ADR 0006)
Exited with code 1
```

The step earns its place. Under session mode all three variants still pass, so without this
check the job would go green with ADR 0006 untested.

## Probe 2 as corrected by PR #17

The replacement is a reasonable probe and its headline claim holds. I reproduced it locally:
a compile error injected into `services/internal/db/db.go`, then `docker compose build`.

```
#13 228.6 internal/db/db.go:123:6: declared and not used: undefinedProbeIdentifier
#13 ERROR: process "/bin/sh -c CGO_ENABLED=0 GOOS=linux go build ... exit code: 1"
target api: failed to solve: ... did not complete successfully: exit code: 1
exit=1
```

The step fails with the compiler output naming the file and the line, which is what the
corrected probe asserts.

The justification sentence next to it is wrong, in the plan and in the `compose.yml` comment
that repeats it ("Building here makes the step fail with compiler output rather than as an
`up --wait` timeout"). It is not a timeout. With the build step removed, Compose builds
during `up`, hits the same compile error, and fails immediately with the same output. I ran
this with the runner's exact Compose version, v2.38.2, from the Compose v2.38.2 release
binary:

```
$ /tmp/opencode/compose238 up -d --wait --wait-timeout 60
#12 174.7 internal/db/db.go:123:6: declared and not used: undefinedProbeIdentifier
target api: failed to solve: ... did not complete successfully: exit code: 1
exit=1
```

So the real benefit of the separate build step is that the failure lands on the step named
for it, and the job does not depend on implicit build behaviour. That is a smaller claim
than the text makes, and worth correcting. No code change is needed.

## Contradictions from the PR #17 change

PR #17 touches four lines of probe 2 and nothing else. I looked for the rest of the plan
disagreeing with it.

`Why build before up` (lines 105-120) already said the daemon starts empty and `up` would
build. The corrected probe now agrees with that section, so the plan is more consistent
after #17 than before. `docs/adr/0007-ci-execution-environment.md` lines 64-69 argue
against cross-run image caches on the grounds that a stale image would be the failure mode
the build step prevents. That argument survives: a cache that survives a run is what would
put a stale image on a fresh daemon.

Two leftovers, both wording:

- The section still opens by calling finding A "the hazard", which reads as though the step
  guards it in CI. The next paragraph says the opposite. The `compose.yml` comment at lines
  56-61 has the same shape.
- Plan line 53 describes step 5 as exporting `VERSION` in the shell. The code writes it to
  `GITHUB_ENV`, and the comment at lines 62-66 explains why a bare export would not survive.
  The implementation is right and the plan text is behind it.
